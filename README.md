# QRDrop POC

> 인터넷이 끊긴 환경(해외여행·비행기·오프그리드)에서 **화면↔카메라**만으로 사진을 친구에게 전송한다.
> 송신 폰은 사진을 잘게 쪼개 QR 시퀀스를 애니메이션으로 띄우고, 수신 폰은 카메라로 그 화면을 촬영·디코딩해 사진을 복원한다.

토스 미니앱 `qrdrop` 컨셉의 **핵심 기술 사전 검증용** 순수 정적 웹(PWA) POC. 토스 SDK 의존성 없음.

---

## 빠른 시작

```bash
npm install
npm run dev          # 자체서명 HTTPS, https://localhost:5173 + https://<로컬IP>:5173
```

- `/send.html` — 사진 선택 → QR 시퀀스 송출
- `/receive.html` — 카메라로 수신 → 사진 복원·저장
- `/selftest.html` — 카메라 없이 전체 파이프라인 자동 검증(아래 참고)

### 모바일(두 폰) 테스트

모바일 브라우저는 카메라(`getUserMedia`)에 **보안 컨텍스트(HTTPS)** 를 요구한다. dev 서버는 `@vitejs/plugin-basic-ssl` 로 자체서명 인증서를 제공한다.

1. PC와 두 폰을 **같은 wifi** 에 연결
2. `npm run dev` 실행 후 출력되는 `https://<로컬IP>:5173` 주소를 두 폰 브라우저에 입력
3. 자체서명 경고가 뜨면 **고급 → 계속 진행**(iOS Safari: "이 웹사이트 신뢰", Android Chrome: "고급 → 안전하지 않음 이동")
4. A폰 `/send.html`, B폰 `/receive.html`
5. ngrok 등 신뢰 인증서가 필요하면: `ngrok http https://localhost:5173` 또는 `mkcert` 로 로컬 CA 설치

> 자체서명이 번거로우면 `mkcert -install && mkcert localhost <로컬IP>` 후 vite `server.https` 에 키/인증서를 지정하는 방식 권장.

## 아키텍처

```
[송신]  사진 → 압축(JPEG) → 블록 분할 → fountain 심볼(무한) → 바이너리 프레임 → QR canvas 애니메이션
[수신]  카메라 → canvas getImageData → jsQR.binaryData → 프레임 파싱 → fountain peeling 복원
```

### 프레임 포맷 (QR byte mode)

**v2 (현재, LT fountain code + raw 바이너리 프레임)** — `src/fountain.ts`

base64 텍스트 프레임을 버리고 **raw 바이너리(QR byte mode)** 로 보낸다. 고정 18바이트 헤더 + 심볼 페이로드(big-endian):
```
off 0  magic 'Q''D''4'    3B
off 3  flags  uint8       bit0 = 암호화됨(AES-256-GCM). 나머지 예약
off 4  seed   uint32      심볼 식별자. seed<k → systematic(블록 seed 단독, degree 1), seed>=k → LT 랜덤 결합
off 8  k      uint16      소스 블록 개수
off 10 len    uint32      페이로드 바이트 길이(마지막 블록 zero-pad 트리밍용)
off 14 sess   uint32      페이로드 djb2 해시(새 사진/다른 전송 혼입 감지)
off 18 payload            블록 크기 B 바이트인 심볼(raw)
```
- 바이트는 `String.fromCharCode` 로 latin1 문자열화해 `addData(s, 'Byte')` 로 인코딩하고(qrcode-generator는 byte mode에서 `charCodeAt&0xff`), 수신은 `jsQR(...).binaryData`(number[])로 원시 바이트를 그대로 복원한다. **base64 33% 오버헤드 제거.**
- 송신은 끝없이 심볼을 찍고, 수신은 순서·중복과 무관하게 **"받은 심볼 ≈ 블록 수 + 소량 오버헤드"** 만 모이면 복원(peeling 디코더). **누락 회복에 사이클 재시청 불필요.**
- systematic 접두 덕분에 **손실 없는 1패스는 v1처럼 1.00× 오버헤드**(블록 그대로 수신), 손실분만 이후 LT 심볼이 메운다 — 두 방식의 장점 결합.

**v1 (legacy)** — `src/protocol.ts`
```
QD1:<idx>:<total>:<sess>:<base64chunk>
```
- base64 문자집합(`A-Z a-z 0-9 + / =`)에 콜론이 없어 `split(':')` 파싱이 안전
- 단순 인덱스 반복 loop. 수신측이 idx로 dedup, 못 받은 청크는 다음 사이클에서 수신.
- **tail 비효율**(막판 몇 청크 누락 시 전체 사이클 재시청)이 v2 fountain으로 해소됨.

### 의존성 (최소)

| 용도 | 라이브러리 | 비고 |
|---|---|---|
| QR 인코딩 | `qrcode-generator` | byte mode, version auto, 직접 canvas 렌더 |
| QR 디코딩 | `jsqr` | 매 프레임 getImageData → 디코딩 |
| 사진 압축 | `browser-image-compression` | maxWidthOrHeight·quality, web worker |
| HTTPS(dev) | `@vitejs/plugin-basic-ssl` | 모바일 카메라 권한용 |

송신 화면에서 **해상도·화질·청크크기·fps·ECC** 를 실시간 슬라이더로 조절 → 실제 대역폭/인식률을 현장에서 튜닝.

## 검증 결과 (자동, 카메라 광학 제외)

POC의 가장 큰 기술 리스크는 **"qrcode-generator로 만든 QR을 jsQR이 실제로 디코딩하는가"** 였다. 카메라 없이 두 단계로 검증.

### 1) Node 라운드트립 — QR 인코더↔디코더 상호운용성 (`node test/roundtrip.mjs`)

payload → QR 모듈매트릭스 → RGBA 버퍼 렌더 → jsQR 디코딩 → 원본 일치. (노이즈 없는 이상적 렌더)

| 청크(chars) | ECC | QR 모듈수 | 결과 |
|---|---|---|---|
| 200~1500 | **M** | 61~145 | **5/5 OK** ✅ |
| 200~1500 | **Q** | 69~173 | **5/5 OK** ✅ |
| 200~1500 | **L** | 53~129 | **4/5** — 1000chars(v23)에서 디코딩 실패 ❌ |

> **발견**: ECC **L** 은 노이즈 없는 깨끗한 렌더에서도 특정 버전에서 jsQR 디코딩이 실패(해상도를 6→12px로 키워도 동일). **M/Q는 전 구간 100%.** → 기본값 **M** 채택, L은 사용 금지 권장.

### 2) 브라우저 전체 파이프라인 (`/selftest.html`, 실제 Chromium 구동)

압축 → 프레임 → QR canvas → `getImageData` → jsQR → 재조립 → **원본 바이트 비교**.

| 항목 | 측정값 |
|---|---|
| 입력(합성 1000×1000 PNG) | 885KB → 압축 **15KB** (maxDim 600, q0.6) |
| 청크 수 | 29 (chunk 700, base64 20KB) |
| QR 모듈수 | ≈105 (version 23, ECC M) |
| 디코딩 실패 | **0 / 29** |
| 디코딩 속도 | **38.8ms/프레임** (≈ 25fps 디코드 여력, 데스크톱) |
| 바이트 일치 | **YES** ✅ — 무손실 복원 |

### 3) 라이브 송신 페이지 (실제 구동 확인)

38KB JPEG 주입 → 압축 18KB → base64 24KB → **36 청크**, 1 사이클 ≈ **4.5초 @ 8fps**, 1017px QR 애니메이션 정상 송출 확인.

### 4) 두 폰 실측 — 맥북(송신) → 아이폰 Safari(수신) ✅

| 항목 | 측정값 |
|---|---|
| 전송 사진 | 인스타 스크린샷, 37KB / 72청크 (chunk 700, ECC M, 8fps) |
| 수신 결과 | **72/72 = 100%, 무손실 복원** ✅ |
| 디코드 능력 | 59 디코드/초 (카메라·CPU 여유 충분) |
| **완료 시간** | **123초** (이론 1사이클 9초 = 13.7사이클 소요) |
| **유효 효율** | **≈ 7%** (이론 4.2KB/s 중 실효 0.3KB/s) |

> **결정적 발견**: 카메라 디코드 능력(59/초)은 차고 넘치는데 **단순 인덱스 반복 loop의 tail 비효율**이 93%를 잡아먹는다. 한 사이클에 평균 ~5청크만 새로 획득 → 막판 몇 청크 못 받으면 72장 사이클을 처음부터 재시청. **병목은 QR 기술이 아니라 재전송 전략.** → **Fountain code(v2)가 최우선 개선**임이 데이터로 확정됨.

### 대역폭 모델 (현장 시간 예측에 사용)

```
프레임당 페이로드 ≈ chunkSize(=base64 chars ≈ bytes) − 헤더(~20B)
유효 전송속도 ≈ chunkSize × fps  (1사이클 손실 0% 가정)
1사이클 시간   ≈ 청크수 / fps = ceil(base64길이 / chunkSize) / fps
```

예) chunk 700 · 8fps → 5.6KB/s(base64) ≈ 4.2KB/s(원본). 200KB 사진이면 base64 ≈ 266KB → **약 48초/사이클**. 카메라가 1사이클에 모든 프레임을 놓치지 않고 잡아야 1회 완료 → 실제론 누락분 재수신으로 1.x~2x 소요 예상.

> ⚠️ **카메라 광학 경로(조도·초점·모아레·디스플레이 주사율 vs fps 동기)** 는 두 폰 실측에서만 검증 가능 — 아래 다음 단계 참고.

### 5) v2 — LT fountain code (`node test/fountain.mjs`) ✅

v1 실측에서 병목으로 확정된 **재전송 전략**을 fountain code로 교체. 임의 손실·중복·순서뒤섞임에서 무손실 복원 및 오버헤드(수신 심볼/블록 수)를 측정.

| 원본 | 블록 수 k | 손실률 | 오버헤드 | 결과 |
|---|---|---|---|---|
| 1.5KB~60KB | 3~115 | **0%** | **1.00×** | **OK** ✅ (systematic = v1 최선과 동일) |
| 13KB~60KB | 25~115 | **20%** | 1.20~1.50× | **OK** ✅ |
| 1.5KB~60KB | 3~115 | **50%** | 1.20~1.43× | **OK** ✅ |

> **핵심**: **50% 프레임을 잃어도 ~1.2~1.4배 심볼만 받으면 복원** — v1처럼 사이클을 처음부터 재시청할 필요가 없다. v1 실측의 93% tail 낭비가 구조적으로 제거됨. 브라우저 전체 파이프라인(`/selftest.html`)은 손실 20% 주입 상태로 QR 렌더↔jsQR↔fountain 디코드까지 무손실 복원을 검증.

### 6) v2 — raw 바이너리 프레이밍 (`node test/binary.mjs`) ✅

base64를 버리고 임의 바이트를 QR byte mode로 직접 전송. 가장 큰 리스크였던 "qrcode-generator↔jsQR이 임의 바이트(0x00·0xFF·구분자·magic 충돌 포함)를 무손실 왕복하는가"를 실제 QR 인코드/디코드로 검증.

| 검증 | 케이스 | 결과 |
|---|---|---|
| 임의 바이트 QR 왕복(binaryData) | 200~1200B × ECC M/Q | **6/6 OK** ✅ |
| 완전한 바이너리 프레임 왕복 | seed=0xffffffff·k=65535·sess=0xffffffff 등 경계값 | **3/3 OK** ✅ |

> **효과**: 페이로드 base64 오버헤드 33% 제거 → 같은 QR 크기에 약 33% 더 많은 실제 바이트를 실어 전송 프레임 수가 줄어든다. 청크 슬라이더 의미도 `chars` → 프레임당 raw `bytes` 로 변경.

### 7) 두 폰 실측 — v2 (Vercel 라이브 도메인, 실사진) ✅

`qrdrop-poc.vercel.app` 배포본으로 실사진(발코니 화분) 전송. **신뢰 HTTPS** 라 자체서명 경고 없이 카메라 즉시 동작.

| 항목 | v1 (검증 4) | **v2 (이번)** |
|---|---|---|
| 전송 사진 | 37KB / 72청크 | **99KB / 146블록** (더 무거운 실사진) |
| 수신 결과 | 72/72 무손실 | **무손실 복원** ✅ |
| 완료 시간 | **123초** | **38.9초** |
| 수신 심볼 / 오버헤드 | — | 233개 / **1.60×** |
| 유효 처리량 | 0.30 KB/s | **2.54 KB/s** |

> **결과**: KB당 **약 8.5배 단축**. v1의 93% tail 낭비가 fountain으로 제거됨이 실환경에서 확인.

#### fps 튜닝 실측 — 더 올리면 오히려 느려진다

같은 99KB 사진을 fps만 바꿔 측정(수신 다운스케일 500px·중복 seed 스킵 적용):

| 송신 fps | 완료 | 수신 심볼 | 오버헤드 |
|---|---|---|---|
| **8** | **38.9초** | 233 | **1.60×** |
| 11 (1회) | 42.6초 | 308 | 2.12× |
| 11 (2회) | 42.8초 | 259 | 1.79× |

> **핵심 발견**: 이 폰의 병목은 송신 속도가 아니라 **깨끗한 프레임 포착 능력**이다. 스캔 15/초 중 유효 읽기는 ~6/초뿐 → 채널이 사실상 **~50% 프레임 손실**. fps를 올리면 각 QR 표시 시간이 짧아져 systematic 패스에서 더 많이 놓치고, fountain이 그만큼 더 메워야 해 **오버헤드가 늘고 더 느려진다.** (시뮬레이션의 50% 손실 오버헤드 ~1.4와 일치 — 코덱은 정상, 손실이 원인.) → **기본 fps 8 유지**.
>
> **완료 시간의 진짜 레버는 블록 수 k**(≈ 압축 후 바이트). 그래서 **기본 압축을 빠른 프리셋(maxDim 480·q0.55)으로** 낮춰 같은 사진을 ~50KB/k~73 수준으로 → 완료 시간 약 절반(~20초) 목표. 화질↔속도는 송신 슬라이더로 현장 조절.

#### 빠른 프리셋 적용 후 실측 (현재 기본값, 같은 사진) ✅

| 설정 | 파일 | 블록 k | 완료 | 수신 심볼 | 오버헤드 |
|---|---|---|---|---|---|
| 최초(화질0.6, fps8) | 99KB | 145 | 38.9초 | 233 | 1.60× |
| **빠른 프리셋(480·q0.55, fps8)** | **62KB** | **91** | **28.8초** | 125 | **1.37×** |

> 완료 **38.9→28.8초(26%↓)**, 오버헤드 **1.60→1.37×**(역대 최저, 이론 ~1.3 근접). 압축으로 k를 줄인 효과가 그대로 시간 단축으로 나타남. 더 줄이려면 슬라이더로 해상도/화질을 추가로 낮추면 됨.

### 8) 비밀번호 E2E 암호화 (`node test/crypto.mjs`) ✅

송신·수신만 아는 비밀번호로 사진을 암호화해 **보안/비밀 전송** 용도로 확장. 화면을 누가 촬영해 "암호문"을 가져가도 비밀번호 없이는 못 연다.

| 검증 | 결과 |
|---|---|
| 올바른 비밀번호 라운드트립 무손실 | OK ✅ |
| 컨테이너 = salt16 + iv12 + 태그16 + 평문 | OK ✅ |
| 틀린 비밀번호 거부(GCM 인증 실패) | OK ✅ |
| 변조된 암호문 거부(무결성) | OK ✅ |

> **방식**(`src/crypto.ts`): PBKDF2-SHA256 **60만 회**로 비밀번호+salt에서 AES-256 키 유도 → **AES-256-GCM** 암호화. 컨테이너 `[salt16 | iv12 | ciphertext+tag]` 를 fountain으로 전송하고, 프레임 헤더 `flags` 비트로 암호화 여부를 표시(수신측이 첫 프레임에서 🔒 인지). WebCrypto만 사용(무의존), 보안 컨텍스트(HTTPS/localhost) 필요.
>
> ⚠️ **보안은 전적으로 비밀번호 강도에 의존**: 누구나 화면을 촬영하면 암호문은 확보 가능하므로, 약한 비번은 오프라인 무차별 대입에 취약. **긴 패스프레이즈 권장.** 비밀번호는 앱 밖 별도 채널로 공유(PSK 모델). 강한 비번이면 녹화당해도 안전 + GCM이 변조까지 탐지.

## 알려진 문제 / 개선 아이디어

- ~~**단순 인덱스 반복**의 tail 비효율~~ → **v2에서 LT fountain code로 해결**(`src/fountain.ts`, 위 검증 5). 받은 심볼 수 ≈ 블록 수만 되면 순서·중복 무관하게 복원.
- ~~**화면 밝기/절전**: Wake Lock 미적용~~ → **v2에서 `navigator.wakeLock` 적용**(송신 중 화면 꺼짐 방지, 미지원 브라우저는 무시, 탭 복귀 시 재획득).
- ~~**base64 33% 오버헤드**~~ → **v2에서 raw 바이너리 프레임(QR byte mode)으로 제거**(`src/fountain.ts`, 검증 6). 17B 고정 헤더 + raw 심볼, `binaryData`로 복원.
- **ECC L 디코딩 취약** (위 검증). 기본 M 유지.
- **fps vs 디스플레이 주사율 동기화**: 송신 fps가 너무 높으면 수신 카메라가 프레임을 건너뜀. 화면 tearing/모아레로 디코딩률 저하 가능 → 현장 튜닝 필요. (fountain은 누락에 강건하므로 fps를 더 공격적으로 올려도 됨)
- **PWA/오프라인**: manifest·service worker 미적용(브라우저 단독 동작은 확인). 오프라인 설치형으로 만들려면 추가.
- **큰 사진**: maxDim/quality를 낮추지 않으면 청크 폭증 → 사이클 시간 비현실적. 현재 기본(600px·q0.6)에서 합성샘플 15~18KB로 양호하나, 디테일 많은 실사진은 더 큼.

## 결론

**핵심 기술은 작동한다.** QR 인코더(qrcode-generator)↔디코더(jsQR) 상호운용성, 브라우저 내 압축·청크·QR렌더·재조립이 무손실로 검증됐다(0 디코딩 실패, 바이트 일치).

**v2** 에서 v1 실측의 진짜 병목(재전송 전략)을 **LT fountain code**로 교체해, 50% 손실에서도 ~1.2~1.4× 심볼만으로 무손실 복원함을 검증했다(사이클 재시청 제거). 또한 **raw 바이너리 프레임(QR byte mode)** 으로 base64 33% 오버헤드를 제거하고, 화면 꺼짐 방지(Wake Lock)도 적용했다. 남은 단 하나의 미검증 변수는 **실제 카메라 광학 경로**이며, 이는 두 폰 실측으로만 확인 가능하다. 위 체크리스트(특히 v1 대비 완료 시간 단축)로 측정 후 컨셉 확정 권장.
