# QRDrop POC

> 인터넷이 끊긴 환경(해외여행·비행기·오프그리드)에서 **화면↔카메라**만으로 사진을 친구에게 전송한다.
> 송신 폰은 사진을 잘게 쪼개 QR 시퀀스를 애니메이션으로 띄우고, 수신 폰은 카메라로 그 화면을 촬영·디코딩해 사진을 복원한다.

토스 미니앱 `qrdrop` 컨셉의 **핵심 기술 사전 검증용** 순수 정적 웹(PWA) POC. 토스 SDK 의존성 없음.

---

## 빠른 시작

```bash
npm install
npm run dev          # 자체서명 HTTPS, https://localhost:5173 + https://<로컬IP>:5173
```

- `/send.html` — 사진 선택 → QR 시퀀스 송출
- `/receive.html` — 카메라로 수신 → 사진 복원·저장
- `/selftest.html` — 카메라 없이 전체 파이프라인 자동 검증(아래 참고)

### 모바일(두 폰) 테스트

모바일 브라우저는 카메라(`getUserMedia`)에 **보안 컨텍스트(HTTPS)** 를 요구한다. dev 서버는 `@vitejs/plugin-basic-ssl` 로 자체서명 인증서를 제공한다.

1. PC와 두 폰을 **같은 wifi** 에 연결
2. `npm run dev` 실행 후 출력되는 `https://<로컬IP>:5173` 주소를 두 폰 브라우저에 입력
3. 자체서명 경고가 뜨면 **고급 → 계속 진행**(iOS Safari: "이 웹사이트 신뢰", Android Chrome: "고급 → 안전하지 않음 이동")
4. A폰 `/send.html`, B폰 `/receive.html`
5. ngrok 등 신뢰 인증서가 필요하면: `ngrok http https://localhost:5173` 또는 `mkcert` 로 로컬 CA 설치

> 자체서명이 번거로우면 `mkcert -install && mkcert localhost <로컬IP>` 후 vite `server.https` 에 키/인증서를 지정하는 방식 권장.

## 아키텍처

```
[송신]  사진 → 압축(JPEG) → base64 → 청크 분할 → 프레임 → QR canvas 애니메이션(loop)
[수신]  카메라 → canvas getImageData → jsQR → 프레임 파싱 → idx dedup 수집 → 전부 모이면 재조립
```

### 프레임 포맷 (QR byte mode, ASCII)

```
QD1:<idx>:<total>:<sess>:<base64chunk>
```

- base64 문자집합(`A-Z a-z 0-9 + / =`)에 콜론이 없어 `split(':')` 파싱이 안전
- **모든 프레임에 메타(total/sess) 포함** → 수신자가 시퀀스 중간에 합류 가능
- `sess` = 전체 base64의 djb2 해시(base36). 새 사진 시작/다른 전송 혼입을 감지해 자동 리셋
- v1 재전송 전략: **단순 인덱스 반복 loop**. 수신측이 idx로 dedup, 못 받은 청크는 다음 사이클에서 수신. (Fountain/LT/RaptorQ는 v2)

### 의존성 (최소)

| 용도 | 라이브러리 | 비고 |
|---|---|---|
| QR 인코딩 | `qrcode-generator` | byte mode, version auto, 직접 canvas 렌더 |
| QR 디코딩 | `jsqr` | 매 프레임 getImageData → 디코딩 |
| 사진 압축 | `browser-image-compression` | maxWidthOrHeight·quality, web worker |
| HTTPS(dev) | `@vitejs/plugin-basic-ssl` | 모바일 카메라 권한용 |

송신 화면에서 **해상도·화질·청크크기·fps·ECC** 를 실시간 슬라이더로 조절 → 실제 대역폭/인식률을 현장에서 튜닝.

## 검증 결과 (자동, 카메라 광학 제외)

POC의 가장 큰 기술 리스크는 **"qrcode-generator로 만든 QR을 jsQR이 실제로 디코딩하는가"** 였다. 카메라 없이 두 단계로 검증.

### 1) Node 라운드트립 — QR 인코더↔디코더 상호운용성 (`node test/roundtrip.mjs`)

payload → QR 모듈매트릭스 → RGBA 버퍼 렌더 → jsQR 디코딩 → 원본 일치. (노이즈 없는 이상적 렌더)

| 청크(chars) | ECC | QR 모듈수 | 결과 |
|---|---|---|---|
| 200~1500 | **M** | 61~145 | **5/5 OK** ✅ |
| 200~1500 | **Q** | 69~173 | **5/5 OK** ✅ |
| 200~1500 | **L** | 53~129 | **4/5** — 1000chars(v23)에서 디코딩 실패 ❌ |

> **발견**: ECC **L** 은 노이즈 없는 깨끗한 렌더에서도 특정 버전에서 jsQR 디코딩이 실패(해상도를 6→12px로 키워도 동일). **M/Q는 전 구간 100%.** → 기본값 **M** 채택, L은 사용 금지 권장.

### 2) 브라우저 전체 파이프라인 (`/selftest.html`, 실제 Chromium 구동)

압축 → 프레임 → QR canvas → `getImageData` → jsQR → 재조립 → **원본 바이트 비교**.

| 항목 | 측정값 |
|---|---|
| 입력(합성 1000×1000 PNG) | 885KB → 압축 **15KB** (maxDim 600, q0.6) |
| 청크 수 | 29 (chunk 700, base64 20KB) |
| QR 모듈수 | ≈105 (version 23, ECC M) |
| 디코딩 실패 | **0 / 29** |
| 디코딩 속도 | **38.8ms/프레임** (≈ 25fps 디코드 여력, 데스크톱) |
| 바이트 일치 | **YES** ✅ — 무손실 복원 |

### 3) 라이브 송신 페이지 (실제 구동 확인)

38KB JPEG 주입 → 압축 18KB → base64 24KB → **36 청크**, 1 사이클 ≈ **4.5초 @ 8fps**, 1017px QR 애니메이션 정상 송출 확인.

### 대역폭 모델 (현장 시간 예측에 사용)

```
프레임당 페이로드 ≈ chunkSize(=base64 chars ≈ bytes) − 헤더(~20B)
유효 전송속도 ≈ chunkSize × fps  (1사이클 손실 0% 가정)
1사이클 시간   ≈ 청크수 / fps = ceil(base64길이 / chunkSize) / fps
```

예) chunk 700 · 8fps → 5.6KB/s(base64) ≈ 4.2KB/s(원본). 200KB 사진이면 base64 ≈ 266KB → **약 48초/사이클**. 카메라가 1사이클에 모든 프레임을 놓치지 않고 잡아야 1회 완료 → 실제론 누락분 재수신으로 1.x~2x 소요 예상.

> ⚠️ **카메라 광학 경로(조도·초점·모아레·디스플레이 주사율 vs fps 동기)** 는 두 폰 실측에서만 검증 가능 — 아래 다음 단계 참고.

## 알려진 문제 / 개선 아이디어

- **ECC L 디코딩 취약** (위 검증). 기본 M 유지.
- **base64 33% 오버헤드**: QR byte mode로 raw 바이너리 직접 전송 시 제거 가능(헤더/페이로드 분리 프레이밍 필요). → 전송시간 ~25% 단축. v2.
- **단순 인덱스 반복**의 tail 비효율: 마지막 몇 청크 못 받으면 사이클을 처음부터 다시 봐야 함. **Fountain code(LT/RaptorQ)** 도입 시 받은 패킷 수 ≈ 청크 수만 되면 순서·중복 무관하게 복원 → 누락 회복 비용 급감. v2 핵심 개선.
- **fps vs 디스플레이 주사율 동기화**: 송신 fps가 너무 높으면 수신 카메라가 프레임을 건너뜀. 화면 tearing/모아레로 디코딩률 저하 가능 → 현장 튜닝 필요.
- **화면 밝기/절전**: 송신 폰 화면 자동 꺼짐 방지(Wake Lock API) 미적용. v2에서 `navigator.wakeLock` 추가 권장.
- **PWA/오프라인**: manifest·service worker 미적용(브라우저 단독 동작은 확인). 오프라인 설치형으로 만들려면 추가.
- **큰 사진**: maxDim/quality를 낮추지 않으면 청크 폭증 → 사이클 시간 비현실적. 현재 기본(600px·q0.6)에서 합성샘플 15~18KB로 양호하나, 디테일 많은 실사진은 더 큼.

## 결론

**핵심 기술은 작동한다.** QR 인코더(qrcode-generator)↔디코더(jsQR) 상호운용성, 브라우저 내 압축·청크·QR렌더·재조립이 무손실로 검증됐다(0 디코딩 실패, 바이트 일치). 남은 단 하나의 미검증 변수는 **실제 카메라 광학 경로**이며, 이는 두 폰 실측으로만 확인 가능하다. 위 체크리스트로 측정 후 컨셉 확정 권장.
